# Keye Decode Indexer 候选机制

## 减少打分时读取的 Index Key 字节

**假设。** Keye 的每个历史位置有一条 64 维 BF16 Key。一个解码查询即使只选 2048 项，仍会触碰整个历史。若用 96 字节固定主体加少量元数据表示一条原占 128 字节的 Key，并在点积 tile 内恢复原位型，长历史、大 batch 的带宽收益可能盖过解码指令。

**方法。** 每个物理 Key 行自行确定非零指数范围。符号与 7 位尾数原样保存，每个维度另用 4 位表示指数增量，为指数零保留编码。超出范围的行保留完整 BF16 值，由行头索引。符号零与次正规数均可还原。正常行的主体 96 字节，行头 4 字节；每个异常行在主体之外另占 128 字节。实际占用还取决于异常区预留、增长策略、历史编码临时空间和是否保留原始 BF16。计算使用模型原有的逐头 BF16 舍入与带符号权重，保留分页访问和逻辑 token 输出。

**与已有研究的关系。** 指数低熵、每值 4 位指数码、异常值旁路和计算中解码均有先例。SplitZip 使用热指数与 escape stream 处理 KV 传输，GAAC 对已校准的通道簇选码宽并在 Attention 内复原，ZipServ 处理模型权重。这里考察的是动态生成的、16 个查询头共用的 64 维 Index Key：以物理 token 行为解码单位，用一份行头支持不规则访问，将数据恢复直接放在 Keye 的 ReLU 加权打分中，并用原生分数核验 Top‑2048。论文贡献应落在这个算子、布局选择和实测适用区间。[SplitZip](https://github.com/Intelligent-Microsystems-Lab/SplitZip) [GAAC](https://arxiv.org/abs/2610.38210) [ZipServ](https://arxiv.org/abs/2603.17435)

**可证伪条件。** 单 token 乱序物理位置可能让多个窄数据流支付额外的 gather 延迟；短行驻留 L2 时，解码本身也可能更慢。应分别测连续布局、按块打散、逐 token 打散、近期热缓存与多个历史轮换。一次性历史编码和每步当前 Key 写入需要分别计时。只有在同一存储布局下真实执行过的后备路径才能纳入结果。

## 压缩页表寻址

历史 token 连续分配时，tile 可以记录第一个物理 slot 并用局部偏移寻址。遇到破碎 tile 时逐 token 读取页表。只修改或追加尾部时可以增量更新该段；请求重排、回收或重映射必须使受影响元数据失效。此机制只改变地址生成，仍计算全部有效分数。最小对照是在同一方向、tile 和选择器下，分别实测普通 gather、每步重建以及尾段维护；不同布局都与原生分数逐项核对。

## 阈值与分段筛选

FlashTopK 将采样、阈值过滤和有恢复的精确选择组合用于多查询 tile。Decode 上样本、分桶与恢复启动可能抵消减少的选择量。比较时保留不含剪枝的 dense 评分与强选择器，另外计量阈值开销、回退和短行。

固定段 Oracle 显示，在 128K、段长 64 时，复现已有 Top‑2048 集合的最大 token 跳过比例中位数为 71.5%。真实粗筛需要在查询到达后计算，间接读取、精算和选择都应计时。按段保留可能混入大量非赢家，按单 token 保留会增加离散访存；两种组织的优劣取决于预算、页布局和边界间隔。近似筛选应同时报告候选覆盖、输出集合、严格高分遗漏及最差行。即使个别输入全命中，也需要数学证书或逐行恢复才能归入精确路径。[Oracle 归档](../../../../my_research_note/projects/horizonkv/branches/main/experiments/2026-11-18_1600_indexer-segment-oracle_v01_draft.md)
